## 1. 产品简介

FixMate 自动拉取并监听分配给用户的飞书缺陷,让 AI 通过修改代码来修复缺陷,用户只负责审核。

- 使用用户自己的 Git 账号和飞书账号。
- 需要用户设置一个工作用的仓库和主分支。
- 收到新缺陷时要有界面通知,全部处理完时也要通知。
- 多个缺陷的修复方案之间可能有关联或冲突,需要专门处理,见第 7 节。

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| 缺陷 | 来自飞书的一条缺陷。缺陷状态是全局的,不属于某个清单 |
| 清单 | 用户自己圈定的一组缺陷。每个缺陷必须在一个或多个清单中 |
| 紧急清单 | 内置清单,置顶,不能编辑和删除,用来插队 |
| 活跃清单 | 当前被 AI 处理的那个清单,同一时间只有一个 |
| 待审核 | AI 修完后等用户审核的缺陷,不占用 AI 执行者 |

清单规则:
- 名称可以重复,但不能为空。系统给每个清单分配唯一 ID,**ID 不在界面上显示**。
- 不在任何清单里的缺陷不会被自动处理。新缺陷到达时默认不在任何清单,界面要提示用户归类。
- 只保留 Auto 工作模式,界面上不出现任何模式提示。

## 3. 队列模型

系统有两层队列,但同一时间只有一个 AI 执行者。

- **清单队列**:已被用户点击处理且没被暂停的清单。紧急清单永远在最前,其余按进入队列的先后顺序。
- **缺陷队列**:活跃清单内按清单顺序,取第一个未处理完的缺陷,一次只处理一个。
- **待审核集合**:AI 不等审核,做完一个直接做下一个。

清单进入队列的规则,**待更新到原型**:
- 开始处理、继续处理、处理完成后又加入新缺陷,清单都**排到清单队列的队尾**,不打断正在处理的清单。
- 只有「优先处理这个清单」能改变顺序,它把清单放到队首,原来正在处理的清单顺延到第二个,进度已保存。
- 对待处理的清单点优先处理,等于开始并插队。连续对两个清单点优先处理,后点的排在最前。
- 被紧急缺陷打断的清单没有离开队列,位置不变,处理完自动恢复。

## 4. 清单状态,共四种(待更新到原型)

「未处理」和「暂停处理」出口相同,都是用户点一下按钮,所以合并为「待处理」,再按数据区分显示。

| 状态 | 谁在推动 | 条件 |
|---|---|---|
| 待处理 | 等用户点击 | 没开始过,或被用户暂停,且还有未处理完的缺陷 |
| 排队中 | 系统 | 用户已点过,前面还有别的清单 |
| 处理中 | 系统 | 用户已点过,并且排在队首 |
| 处理完成 | 系统 | 没有未处理完的缺陷 |

| 从 | 到 | 触发 |
|---|---|---|
| 待处理 | 处理中或排队中 | 用户点开始或继续,清单排到队尾 |
| 排队中 | 处理中 | 前面的清单处理完,或被暂停 |
| 处理中 | 排队中 | 紧急缺陷插队,或用户对别的清单点优先处理 |
| 处理中或排队中 | 待处理 | 用户点暂停 |
| 处理中 | 处理完成 | 最后一个未处理完的缺陷处理完 |
| 处理完成 | 处理中或排队中 | 加入新的未处理缺陷,自动进入队尾 |

显示区分:
- 没有进度时,按钮是「开始处理」。
- 有进度时,多一行「上次停在某缺陷,已处理 N/M」,按钮改成「继续处理」。
- 有没有进度,直接从缺陷数据算出来,不单独存标记。
- 为避免和缺陷的叫法冲突,清单的等待状态统一叫「排队中」。

紧急清单的差别:不会排队,没有开始按钮,加入缺陷后自动开始。为空时显示「空闲」。

## 5. 缺陷状态,共七种

AI 视角下,前三种是未处理完,后四种是已处理。

| 状态 | 说明 |
|---|---|
| 排队中 | 等轮到。所在清单没在处理时,界面显示为「未开始」,仍是同一个状态 |
| AI 处理中 | 分四步:判断是否可修复、建临时分支、改代码并提交、等待审核 |
| 已暂停 | 记住停在哪一步和中间结果 |
| 待审核 | 修复完成,等用户处理。可带「待复核」标记 |
| 已接受 | 终态 |
| 已拒绝 | 终态,可选择保留修改 |
| 已跳过 | 终态,必须有原因 |

| 从 | 到 | 触发 |
|---|---|---|
| 排队中 | AI 处理中 | 成为活跃清单里第一个未处理完的缺陷,从第一步开始 |
| AI 处理中 | 已暂停 | 用户暂停缺陷或清单;清单让位给紧急缺陷或优先清单;缺陷被移出清单 |
| 已暂停 | AI 处理中 | 清单恢复且它排第一,从暂停的那一步继续。被插队打断且 main 已更新时,先同步最新 main |
| AI 处理中 | 待审核 | 修复完成 |
| AI 处理中 | 已跳过 | AI 判断不是改代码能解决的确定问题 |
| 待审核 | 已接受 | 用户接受,随后合并、push、打包、回写飞书 |
| 待审核 | 已拒绝 | 用户拒绝,可选保留修改 |
| 待审核 | 已跳过 | 用户跳过并写原因 |

在用户暂停缺陷和清单被打断这两种情况下,缺陷都是「已暂停」,但行为不同:前者要用户手动继续,后者自动恢复。目前靠一个隐藏标记区分,见第 11 节。

## 6. 接受、拒绝、跳过的流程

接受后系统依次完成:
1. 切到主分支。
2. 把临时分支上的提交 cherry-pick 到主分支。
3. 删除临时分支。
4. push。
5. 通过 Jenkins 接口打 OTA,记录版本号。
6. 在飞书把缺陷标记为已解决。
7. 在飞书评论里写 `#{ota_version}`。

拒绝时用户可选:保留修改,用 `git cherry-pick -n` 放入主分支工作区但不提交;或丢弃,只删临时分支。跳过必须写简短原因。

## 7. 缺陷之间的关联与冲突

- 一个缺陷的修复方案生成于用户还在审核别的方案期间时,标记为「待复核」。
- 每个缺陷修完后缓存结论摘要。轮到审核它时,AI 结合最新代码和缓存结论重新评估,既消除关联问题,又节省 token。
- 详情页的关联提示列出与哪个缺陷修改了同一文件。

## 8. 紧急处理

- 缺陷详情和搜索结果里,未处理完的缺陷都有「立即处理」,点击后进入紧急清单。
- 紧急队列空闲时,直接开始。
- 紧急队列里已有缺陷时,二选一:「马上处理」会打断当前紧急缺陷,「排在紧急队列后面」则不打断。
- 被打断的缺陷保存进度,按后进先出的顺序自动恢复。
- 任何页面顶部都有紧急提示条,点击可打开对应缺陷。
- 紧急缺陷被接受后 main 已更新,被打断的缺陷恢复时要先同步最新 main,再结合缓存结论快速复核。

## 9. 界面结构

- 左侧竖栏:缺陷、清单、搜索三个核心页签,下方一条横线,线下是通知和设置。
- **缺陷页**:显示一个清单里的缺陷,标题就是清单名,点击可切换清单。按清单顺序平铺并带序号,有「去审核」入口。
- **清单页**:卡片网格,整卡可点击并跳到缺陷页,悬停有上浮和箭头提示。有未入清单缺陷时显示提示条。
- **搜索页**:按标题模糊搜索全部缺陷,结果显示所属清单。
- **缺陷详情**:占半屏的右侧侧栏。头部显示编号、状态、优先级、飞书链接,需求和规划版本各占一行。可添加到清单或从清单删除。
- **新建和编辑清单**:占半屏的右侧侧栏,顶部固定名称和筛选,支持全选和清空,底部固定保存。
- 筛选条件:缺陷类型、优先级、规划版本、关联需求。

## 11. 风险和待讨论的问题

**部署在打包机的风险**
- 安全:缺陷内容任何人都能写,可能夹带指令诱导 Claude Code 读取签名密钥或外传数据。需要专用低权限用户、读不到密钥、限制网络、工具白名单,最好用沙箱。
- 资源:多个会话和独立工作目录会拖慢正式打包,要限制并发并清理磁盘。
- 多人共用:拒绝并保留修改需要重新设计,例如推到个人分支或生成补丁;多人同时接受会争抢 main,要加排队或锁;Git 推送身份和飞书授权要每人一份。

**LangGraph 的限制**
- 暂停只能停在节点边界,正在进行的一次模型调用或改代码动作无法冻结,需要把长步骤拆细。
- 检查点只存流程状态,不存文件,所以每个缺陷需要独立工作目录,恢复时要核对目录状态。

**现有设计中已发现的问题**
- 缺陷状态是全局的,同一个缺陷在两个清单里共用一个状态,是否符合预期待定。
- 「已暂停」混了用户暂停和被插队打断两种情况,可考虑拆成两个状态。
- 没有失败状态:AI 改失败、合并冲突、打包失败、接受流程中途出错。
- 终态不能回退,误跳过或误拒绝后无法重新打开。
- 「处理完成」不等于审核完成,界面上只用小字提示待审核数量。

**尚未讨论的话题**
- 异常和失败的处理。
- 飞书侧变化:缺陷被改派、关闭、改了描述或优先级、被重新打开。
- 审核体验:大量待审核时的批量操作,审核时想微调代码。
- 已接受并打包后的撤回或回滚。
- 清单规则:跨清单的状态归属、清单共享、按条件自动入清单。
- 提醒:哪些情况必须打扰用户,哪些静默记录。
