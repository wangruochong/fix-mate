## 1. 产品简介

FixMate 自动拉取并监听分配给用户的飞书缺陷,让 AI 通过修改代码来修复缺陷,用户只负责审核。

- 使用用户自己的 Git 账号和飞书账号。
- 需要用户设置一个工作用的仓库和主分支。
- 收到新缺陷时要有界面通知,全部处理完时也要通知。
- 多个缺陷的修复方案之间可能有关联或冲突,需要专门处理,见第 7 节。

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| 缺陷 | 来自飞书的一条缺陷。缺陷状态是全局的,不属于某个清单 |
| 清单 | 用户自己圈定的一组缺陷。每个缺陷必须在一个或多个清单中 |
| 紧急清单 | 内置清单,置顶,不能编辑和删除,用来插队 |
| 活跃清单 | 当前被 AI 处理的那个清单,同一时间只有一个 |
| 待审核 | AI 修完后等用户审核的缺陷,不占用 AI 执行者 |

清单规则:
- 名称可以重复,但不能为空。系统给每个清单分配唯一 ID,**ID 不在界面上显示**。
- 不在任何清单里的缺陷不会被自动处理。新缺陷到达时默认不在任何清单,界面要提示用户归类。
- 只保留 Auto 工作模式,界面上不出现任何模式提示。

## 3. 队列模型

系统有两层队列,但同一时间只有一个 AI 执行者。

- **清单队列**:已被用户点击处理且没被暂停的清单。紧急清单永远在最前,其余按进入队列的先后顺序。
- **缺陷队列**:活跃清单内按清单顺序,取第一个未处理完的缺陷,一次只处理一个。
- **待审核集合**:AI 不等审核,做完一个直接做下一个。

清单进入队列的规则,**待更新到原型**:
- 开始处理、继续处理、处理完成后又加入新缺陷,清单都**排到清单队列的队尾**,不打断正在处理的清单。
- 只有「优先处理这个清单」能改变顺序,它把清单放到队首,原来正在处理的清单顺延到第二个,进度已保存。
- 对待处理的清单点优先处理,等于开始并插队。连续对两个清单点优先处理,后点的排在最前。
- 被紧急缺陷打断的清单没有离开队列,位置不变,处理完自动恢复。

## 4. 清单状态,共四种(待更新到原型)

「未处理」和「暂停处理」出口相同,都是用户点一下按钮,所以合并为「待处理」,再按数据区分显示。

| 状态 | 谁在推动 | 条件 |
|---|---|---|
| 待处理 | 等用户点击 | 没开始过,或被用户暂停,且还有未处理完的缺陷 |
| 排队中 | 系统 | 用户已点过,前面还有别的清单 |
| 处理中 | 系统 | 用户已点过,并且排在队首 |
| 处理完成 | 系统 | 没有未处理完的缺陷 |

| 从 | 到 | 触发 |
|---|---|---|
| 待处理 | 处理中或排队中 | 用户点开始或继续,清单排到队尾 |
| 排队中 | 处理中 | 前面的清单处理完,或被暂停 |
| 处理中 | 排队中 | 紧急缺陷插队,或用户对别的清单点优先处理 |
| 处理中或排队中 | 待处理 | 用户点暂停 |
| 处理中 | 处理完成 | 最后一个未处理完的缺陷处理完 |
| 处理完成 | 处理中或排队中 | 加入新的未处理缺陷,自动进入队尾 |

显示区分:
- 没有进度时,按钮是「开始处理」。
- 有进度时,多一行「上次停在某缺陷,已处理 N/M」,按钮改成「继续处理」。
- 有没有进度,直接从缺陷数据算出来,不单独存标记。
- 为避免和缺陷的叫法冲突,清单的等待状态统一叫「排队中」。

紧急清单的差别:不会排队,没有开始按钮,加入缺陷后自动开始。为空时显示「空闲」。

## 5. 缺陷状态,共七种

AI 视角下,前三种是未处理完,后四种是已处理。

| 状态 | 说明 |
|---|---|
| 排队中 | 等轮到。所在清单没在处理时,界面显示为「未开始」,仍是同一个状态 |
| AI 处理中 | 分四步:判断是否可修复、创建 worktree 和临时分支、改代码并提交、等待审核 |
| 已暂停 | 记住停在哪一步和中间结果 |
| 待审核 | 修复完成,等用户处理。可带「待复核」标记 |
| 已接受 | 终态 |
| 已拒绝 | 终态,可选择保留修改 |
| 已跳过 | 终态,必须有原因 |

| 从 | 到 | 触发 |
|---|---|---|
| 排队中 | AI 处理中 | 成为活跃清单里第一个未处理完的缺陷,从第一步开始 |
| AI 处理中 | 已暂停 | 用户暂停缺陷或清单;清单让位给紧急缺陷或优先清单;缺陷被移出清单 |
| 已暂停 | AI 处理中 | 清单恢复且它排第一,从暂停的那一步继续。被插队打断且 main 已更新时,先同步最新 main |
| AI 处理中 | 待审核 | 修复完成 |
| AI 处理中 | 已跳过 | AI 判断不是改代码能解决的确定问题 |
| 待审核 | 已接受 | 用户接受,随后合并、push、打包、回写飞书 |
| 待审核 | 已拒绝 | 用户拒绝,可选保留修改 |
| 待审核 | 已跳过 | 用户跳过并写原因 |

在用户暂停缺陷和清单被打断这两种情况下,缺陷都是「已暂停」,但行为不同:前者要用户手动继续,后者自动恢复。目前靠一个隐藏标记区分,见第 11 节。

## 6. 接受、拒绝、跳过的流程

接受后系统依次完成:
1. 切到主分支。
2. 把临时分支上的提交 cherry-pick 到主分支。
3. 删除临时分支。
4. push。
5. 通过 Jenkins 接口打 OTA,记录版本号。
6. 在飞书把缺陷标记为已解决。
7. 在飞书评论里写 `#{ota_version}`。

接受是**七步固定流程,中途可能失败**。失败时缺陷仍是「待审核」(不增加状态),界面说明卡在第几步和原因,用户再点接受会**从失败的那一步继续,已完成的步骤不会重做**。每一步的进度落在业务库里,程序崩溃后重启也以它为准。重做是否安全因步骤而异:
- 切 main、放进 main(先检查 main 里是否已有这个修复)、删分支、推送、标记已解决,可以安全重做。
- **打 OTA 包**(会打两个包)和**飞书评论**(会重复评论)不能安全重做:上次在这两步中断后,第一次重试会被拦下,提示用户先去 Jenkins 或飞书确认是否已生效;用户再点一次才视为确认并继续。
- 推送被拒绝(远端有新提交)时,重新对齐远端后再放一次修复并重试**一次**,绝不强推。放进 main 遇到冲突时撤销,保持 main 干净。

拒绝时用户可选:保留修改,用 `git cherry-pick -n` 放入主分支工作区但不提交;或丢弃,只删临时分支。跳过必须写简短原因。

## 7. 缺陷之间的关联与冲突

- 一个缺陷的修复方案生成于用户还在审核别的方案期间时,标记为「待复核」。
- 每个缺陷修完后缓存结论摘要。轮到审核它时,AI 结合最新代码和缓存结论重新评估,既消除关联问题,又节省 token。
- 详情页的关联提示列出与哪个缺陷修改了同一文件。

## 8. 紧急处理

- 缺陷详情和搜索结果里,未处理完的缺陷都有「立即处理」,点击后进入紧急清单。
- 紧急队列空闲时,直接开始。
- 紧急队列里已有缺陷时,二选一:「马上处理」会打断当前紧急缺陷,「排在紧急队列后面」则不打断。
- 被打断的缺陷保存进度,按后进先出的顺序自动恢复。
- 任何页面顶部都有紧急提示条,点击可打开对应缺陷。
- 紧急缺陷被接受后 main 已更新,被打断的缺陷恢复时要先同步最新 main,再结合缓存结论快速复核。

## 9. 界面结构

- 左侧竖栏:缺陷、清单、搜索三个核心页签,下方一条横线,线下是通知和设置。
- **缺陷页**:显示一个清单里的缺陷,标题就是清单名,点击可切换清单。按清单顺序平铺并带序号,有「去审核」入口。
- **清单页**:卡片网格,整卡可点击并跳到缺陷页,悬停有上浮和箭头提示。有未入清单缺陷时显示提示条。
- **搜索页**:按标题模糊搜索全部缺陷,结果显示所属清单。
- **缺陷详情**:占半屏的右侧侧栏。头部显示编号、状态、优先级、飞书链接,需求和规划版本各占一行。可添加到清单或从清单删除。
- **新建和编辑清单**:占半屏的右侧侧栏,顶部固定名称和筛选,支持全选和清空,底部固定保存。
- 筛选条件:缺陷类型、优先级、规划版本、关联需求。

## 10. 技术方向

已确认:
- AI 引擎使用 **Python 版 LangGraph**,改代码使用 **Claude Code**(通过 claude-agent-sdk)。引擎有两张图:修复图(判断、建分支、改代码、整理)和接受图(七步)。
- 暂停恢复 = LangGraph 的检查点 + Claude Code 的会话恢复。暂停时 AI 在安全的地方停下,未提交的修改存成临时提交,工作目录删除;恢复时重建目录并同步最新 main,用保存的会话号接着对话。
- **工作仓库是 FixMate 专用的克隆**:所有分支、工作目录、接受操作(切 main、cherry-pick、push)都只发生在里面,不碰用户日常开发的工作区。
- 后端使用 **Python + FastAPI**,所有业务放在一个后端服务里。数据结构用 Pydantic 模型定义,与前端 `web/src/types/` 一一对应;接口为 REST 加 SSE,见 `web/README.md`。
- 前端使用 **React + TypeScript + Vite**,做单页应用;组件库用 **shadcn/ui + Tailwind**;数据用 TanStack Query,状态变化由后端通过 SSE 推送。
- 前端由 AI 编写和维护,用户不审查前端代码,所以选型优先考虑生态成熟、类型约束强(缺陷和清单的状态用 TypeScript 联合类型表达)。
- **服务部署在用户本地**,每个人运行自己的一份,使用自己的 Git 账号、飞书账号和 Claude Code 登录。不放在打包机上,避免多人共用和打包机上的安全风险。接受后的打包仍通过 Jenkins 接口触发。
- 界面外观要求:**简洁、美观、优雅**。克制用色,留白充足,细节统一,不堆砌装饰。以现有原型的布局为基础,正式版不使用 Ant Design 这类偏后台风格的组件库。

倾向,未最终确定:
- 先做**网页版**,成熟后再考虑做成桌面应用。
- 后期可能从网页移植为桌面应用,外壳倾向先用 **pywebview** 验证(体积小、仍是 Python 一种语言),需要托盘、原生通知、自动更新等能力时再换 Tauri。前端不受影响,换外壳成本低。

项目命名:
- 仓库和文件夹统一命名为 `fix-mate`,全小写,连字符分隔。
- 后端的 Python 包名使用 `fix_mate`,因为包名不能带连字符。
- 界面和文档里的产品名仍然是 FixMate。
- 建立 Git 仓库后,原型的历史版本文件不再保留副本,从 Git 历史中查看。

已验证的技术结论(2026-11,用小脚本实测,LangGraph 1.2、claude-agent-sdk 0.2、git 2.50):
- **LangGraph 暂停恢复**:无论是取消任务、节点抛异常还是 `interrupt()`,检查点都停在已完成的节点之后;用同一个 `thread_id` 调 `ainvoke(None, config)` 会只重跑没完成的节点,换新的检查点连接和图对象(相当于进程重启)也能恢复。所以**未完成的节点必须能安全重跑**。`stream_mode="tasks"` 能拿到节点开始和结束的事件,用来更新界面的步骤。
- **Claude Agent SDK**:`ResultMessage.session_id` 可用 `resume` 恢复,上下文保留且 session_id 不变;`client.interrupt()` 后流程正常结束,收到的 `ResultMessage.subtype` 是 `error_during_execution`(调用方自己发的打断,不当作失败)。`setting_sources=[]` 可避免被本机的配置和 hook 影响。
- **git worktree**:同一分支不能在两个目录检出;有未提交修改的目录不能直接删除(所以暂停前先提交 wip);提交后删目录、分支保留、之后能重建;变基和压成单个提交(`reset --soft`)可行;推送被拒绝后可以 fetch、reset、重新 cherry-pick 再推;冲突的 cherry-pick 用 `--abort` 能回到干净状态;`git merge-tree --write-tree` 能在不动工作区的情况下预检冲突(冲突时返回码为 1)。

- **LangGraph 的恢复要靠入口条件边**:暂停后恢复时,工作目录已经删除,只重跑「没完成的节点」会指向一个不存在的目录。做法是用同一个 thread_id 再运行一次,图的入口有条件边(已经判断过可修复的直接从「准备工作目录」开始,不用重新判断),状态里已有的结果保留。`AsyncSqliteSaver` 的表要主动 `setup()`,否则第一次就删除旧检查点会报「no such table」。
- **Claude Agent SDK 的结构化输出是通过调用 `StructuredOutput` 工具实现的**。安全守卫采用「白名单、默认拒绝」,必须放行这个内部工具,否则 AI 交不回结构化结果(真实集成测试发现的)。守卫用 `PreToolUse` 钩子,对所有工具调用生效(包括已被自动批准的),`on_failure="block"` 保证守卫自己出错时也拦下。
- **git cherry-pick 的「是否已放进 main」要两个判断合起来**:原提交已是 main 的祖先(提交刚好建立在当前 main 上时,cherry-pick 可能生成同一个提交),或 `git cherry` 标出内容等价的提交。这让接受流程中途重试时不会把同一个修复放进去两次。

建议的结构:界面只负责展示,所有业务放在一个后端服务里。调度层只认开始、暂停、恢复和事件流这几个接口,引擎可以替换。

## 11. 风险和待讨论的问题

**本地部署的风险**
- 安全:缺陷内容任何人都能写,可能夹带指令诱导 Claude Code 读取本机的密钥、凭据或外传数据。**已实现的防护**:可用工具只有读写文件(没有命令行和网络),每次工具调用前校验路径(限定在该缺陷的工作目录内、挡住 `..` 和符号链接绕行、禁止碰 `.env`、密钥、证书、签名配置、`.git` 和 `.claude`),每个缺陷有费用和轮数上限及整体超时,缺陷文本在提示词里被明确标注为「资料而不是指令」。后端只监听本机并校验 Host 和 Origin,防止网页跨站调用。仍建议不要在能访问生产凭据的机器上运行。
- 休眠和关机:电脑休眠时无法监听新缺陷,需要定时轮询,唤醒后补拉,并在界面上说明最后一次同步的时间。
- 环境安装:每个用户都要装好 Python 环境和 Claude Code 并登录,安装流程要尽量简单,首次启动页要检查这些依赖。
- 占用本机资源:AI 处理时会占用 CPU 和网络,可能影响用户自己的工作,需要限制并发(目前同一时间只处理一个缺陷)。

**LangGraph 的限制**
- 暂停只能停在节点边界,正在进行的一次模型调用或改代码动作无法冻结,需要把长步骤拆细。
- 检查点只存流程状态,不存文件,所以每个缺陷需要独立工作目录,恢复时要核对目录状态。
- 独立工作目录用 **git worktree** 实现,和临时分支结合使用。分支长期保存修改,目录只是临时工作台:AI 开始处理时创建,修完提交进入待审核、或暂停(先把进度提交到分支)时删除,恢复时再创建。这样同一时间通常只有 1 个目录,待审核的缺陷只保留分支。
- worktree 的注意事项:同一分支同时只能在一个目录检出(接受流程在专用克隆的主工作区里切 main,已确定);程序异常退出后启动时会清理失效的目录记录;新目录里项目依赖和构建缓存可能缺失,取决于仓库类型(Android、iOS 等),待摸清。

**现有设计中已发现的问题**
- 缺陷状态是全局的,同一个缺陷在两个清单里共用一个状态,是否符合预期待定。
- 「已暂停」混了用户暂停和被插队打断两种情况,可考虑拆成两个状态。
- 失败状态的完整设计还没有。目前的临时做法:AI 修复流程失败(出错、同步 main 冲突、AI 没有产生任何修改)时,缺陷变为「已暂停」并在原因里说明,需用户手动继续;接受流程失败时,缺陷保持「待审核」并显示卡在第几步。这些「等用户处理」的缺陷调度不会自动重试,也不会挡住排在后面的清单。是否需要独立的「失败」「接受中」状态待定。
- 终态不能回退,误跳过或误拒绝后无法重新打开。
- 「处理完成」不等于审核完成,界面上只用小字提示待审核数量。

**尚未讨论的话题**
- 异常和失败的处理(含上面的完整失败状态)。
- 「拒绝并保留修改」:把改动放进用户日常工作区(要求工作区干净),目前只保留分支,没有写进工作区。
- 飞书侧变化:缺陷被改派、关闭、改了描述或优先级、被重新打开。
- 「待复核」的判断规则和复核的具体做法:目前的规则较粗(只要清单里还有别的待审核缺陷就标记,且只在生成时判断一次),复核结果在原型里是预设文本。待核心功能完成后再深入,可能的方向是记录方案的基线提交,并按改动文件是否重叠来判断。

- 已接受并打包后的撤回或回滚。
- 清单规则:跨清单的状态归属、清单共享、按条件自动入清单。
- 提醒:哪些情况必须打扰用户,哪些静默记录。

## 14. 后端与 AI 引擎

代码在 `backend/`,运行方式、环境变量、代码地图和 AI 引擎的阅读顺序见 `backend/README.md`。

**分层**:`domain/`(纯业务规则,和前端类型一一对应)→ `engine/`(AI 引擎)→ `adapters/`(git、Claude Code、假的飞书和 Jenkins)→ `services/`(调度器和用户操作)→ `store/`(SQLite)→ `api/`(REST 加 SSE)。引擎只通过 `engine/external.py` 里的接口接触外部系统,所以可以换成假实现测试。

**调度**:`domain/schedule.py` 的 `decide()` 回答「现在该暂停谁、该开始谁」(纯函数);`services/scheduler.py` 负责执行。同一时间只有一个 AI 执行者。需要用户手动继续的缺陷(用户暂停的、处理出错的)不算「可以自动做的活」,调度跳过它们,清单里只剩这类缺陷时清单是「待处理」,不挡后面的清单;用户明确点「继续」时才把它们转成可自动恢复。

**并发**:所有修改在一把锁下进行;执行器的回调只入消息队列,由一个协程拿锁后依次处理,所以执行器不会因等锁卡住;每次处理带编号,过期的回调直接丢弃;暂停和完成同时发生时,已做完的结果不会丢(执行器同步登记结果,暂停时先查)。

**存储**:业务库和检查点库是两个文件;业务库是唯一真相,检查点只是辅助。重要的进度(接受流程做到哪一步、AI 会话号)都落在业务库里。启动时会收拾上次异常退出的现场:处理中的缺陷转为「被插队而暂停」自动恢复,做了一半的接受标出卡在哪一步等用户确认。

**当前状态**:修复流程、接受流程、真实 git 操作、真实 Claude Code 集成(带安全限制)都已完成并有测试。**还没有**:真实的飞书和 Jenkins(接口已定,只缺实现),所以目前只能在开发模式下使用;「拒绝并保留修改」;复核的真实做法;失败状态的完整设计。
